Photographer Face Recognition Platform

Full architecture, tech stack, system design & cost plan — built for lowest cost with best accuracy.

What we're building

A web platform where photographers upload event photos to Google Drive, and clients visit the website, take a selfie, and instantly see all photos featuring their face — which they can then view and download.

📸

Photographer side

Uploads photos to a linked Google Drive folder (which they already do). A background sync pulls new photos, runs face detection, and indexes everyone's facial embeddings in a database.

👤

Client side

Client visits the website, takes a quick selfie via webcam or phone camera. The system matches their face against all indexed photos and shows only their photos — downloadable instantly.

🤖

AI engine

Face detection + facial embedding (vector representation of face). Uses open-source AI models — no per-image API cost. All processing can run on free cloud tiers.

Key insight: The "magic" is facial embeddings — every face becomes a list of ~512 numbers. To find a person's photos, we just find all stored embeddings that are close (within a distance threshold) to the selfie's embedding. No retraining, no AI cost per query.

Core capabilities

Google Drive sync — Auto-import photos from Drive folders via Google Drive API
Batch face indexing — Process all photos offline, store face embeddings in DB
Selfie-to-search — Client uploads selfie → face extracted → matched against DB

Face recognition — how it works

The AI pipeline has two stages: indexing (runs once per photo) and search (runs when client submits selfie).

Stage 1 — Photo indexing (background job)

1

Download photo from Drive

Temporarily download the image from Google Drive to server memory or temp storage.

2

Face detection

Use RetinaFace or MTCNN to find all faces in the image. Returns bounding box coordinates for each face found. One photo may contain 10–50 faces at an event.

3

Face alignment

Crop and align each detected face (eyes, nose landmark alignment). This is critical for accuracy — unaligned faces give poor embeddings.

4

Embedding extraction

Run the ArcFace model on each aligned face. Output: a 512-dimensional vector (list of 512 numbers) that uniquely represents that face. This is stored in the database.

5

Store in database

Save (photo_id, face_embedding_vector) in PostgreSQL with pgvector. The photo file stays on Drive — we only store the vector.

Stage 2 — Client selfie search

1

Client takes selfie

Via webcam or phone camera on the website. Image is sent to backend via POST request.

2

Extract selfie embedding

Same face detection + ArcFace pipeline. Extracts a 512-dim vector from the selfie face. Selfie is then discarded — never stored.

3

Vector similarity search

Use pgvector's cosine similarity search: ORDER BY embedding <=> query_embedding LIMIT 200. Finds all stored face embeddings within a distance threshold (e.g. 0.4 cosine distance).

4

Return matched photos

Deduplicate by photo_id (same photo may appear if multiple of their faces were detected). Return Drive thumbnail URLs for the gallery.

Model recommendation

InsightFace (ArcFace)

Recommended

State-of-the-art open-source model. 99.83% accuracy on LFW benchmark. ONNX export available — runs on CPU without GPU. Best balance of accuracy and speed.

Python
ONNX
CPU-friendly

DeepFace

Alternative

Python library that wraps ArcFace, Facenet, VGG-Face and others. Easier to set up but slightly slower. Good for getting started quickly.

Python
Multi-model
Easy setup
Accuracy tip: Set your similarity threshold carefully. Too strict = misses real matches. Too loose = false positives (shows wrong person's photos). Start at 0.4 cosine distance for ArcFace and tune based on real test data from the photographer.

Google Drive integration

The photographer keeps using Google Drive as they already do. The platform connects once and handles everything automatically.

Setup flow (done once)

1

Create Google Cloud project

Free. Enable the Google Drive API. Create OAuth 2.0 credentials (Web Application type).

2

Photographer logs in with Google

One-time OAuth login. Grant permission: "Can read your Drive files". Access token + refresh token stored (encrypted) in the database.

3

Photographer selects event folder

On the admin dashboard, photographer picks a Drive folder for each event (e.g. "Wedding - Sharma Family"). The folder ID is saved.

4

Enable Drive push notifications

Register a webhook on the folder. Google Drive will call your backend URL whenever new photos are added. Automatically triggers processing.

Ongoing sync

Two sync methods (use both)

Webhooks (push) — Drive notifies your server instantly when a new file is added. Process new photos immediately. Free and real-time.
Polling fallback — Every 30 mins, scan the folder for any files you haven't processed yet. Catches anything missed by webhooks (Drive webhooks expire after 7 days and need renewal).

Key Drive API operations needed

files.list — List all images in a folder
files.get — Get file metadata (name, size, created time)
files.get (alt=media) — Download file content for processing
files.get (fields=thumbnailLink) — Get Drive's built-in thumbnail for gallery display
channels.watch — Register webhook to monitor folder changes
Smart thumbnail trick: Don't re-host photos. Use Google Drive's built-in thumbnail URLs (?sz=400 parameter) directly in your gallery. Photos only download from Drive when the client clicks to get the full-res image. This keeps your bandwidth and storage at zero cost.
Drive API quotas: Free tier allows 10,000 queries/100 seconds and 1 billion queries/day. Well above what a photography business needs. But batch processing should use exponential backoff to avoid quota errors.

User flows

Photographer flow

1

Sign up / Login

Photographer goes to yourdomain.com/admin and signs in with their Google account.

2

Create event

Clicks "New Event" → enters event name → picks the Google Drive folder that contains (or will contain) the photos → saves.

3

Upload photos (as usual)

Photographer continues uploading to their Google Drive folder as they always do. No change in workflow.

4

Platform indexes in background

System detects new files (via webhook), downloads, processes, and stores face embeddings. Progress shown on admin dashboard.

5

Share link with clients

Photographer copies the event's public URL (e.g. yourdomain.com/event/sharma-wedding) and sends to all guests via WhatsApp, email, etc.

Client (photo recipient) flow

1

Visit event link

Client opens the link on phone or laptop. Sees the event name and a "Find my photos" button.

2

Take a selfie

Browser asks for camera permission. Client takes a selfie or uploads a clear face photo. A face-detection indicator confirms a face was found before allowing submission.

3

Wait 2–5 seconds

Server extracts embedding from selfie, runs similarity search across all indexed embeddings for this event. Selfie is deleted.

4

View gallery

All matching photos shown in a clean gallery. Client can tap any photo to see full size, or click "Download all" to get them as a ZIP.

5

Download

Individual downloads served directly from Google Drive. "Download all" creates a ZIP of Drive file links on the backend and streams it to the user.

No account needed for clients. Clients don't need to sign up or log in. This is intentional — it removes friction. The only "auth" is their face.
